# App Flow Document

## Onboarding and Launch
When a user first interacts with ChessBomb Editor, they usually download a standalone executable or open the application from their development environment. Once they double-click the application icon, a brief splash screen appears while the program loads all needed assets such as piece and skull images, fonts, and configuration settings. There is no account system or sign-in screen, so the user is taken directly into the main editor once initialization finishes. If any asset fails to load, a simple error dialog informs the user which file is missing, and the application exits or returns them to the splash screen so they can resolve the issue.

## Main Editor Window
After launch, the user sees the Pygame-based ChessBomb Editor window. At the center is an 8×8 grid representing the puzzle board. Along the left edge, the user finds controls to choose which skull type to place and counters showing how many of each chess piece are available. At the top sits the application title and tooltips that briefly explain the current mode. The bottom of the window displays action buttons labeled “Solve,” “Clear Board,” and “Reset Counts.” If the user clicks “Solve,” a progress indicator appears near the bottom right. There is no separate menu bar, so these controls serve as the main navigation for core actions. From this window the user can switch between placing skulls, editing piece counts, or launching the solver.

## Board Configuration Flow
To configure a new puzzle, the user moves their mouse over any cell in the grid. A left click places the currently selected skull type there, while a right click removes a skull. If the user wants to change to a different skull, they click the skull icon in the left control panel, toggling between skull types. As they place or remove skulls, the grid updates immediately, coloring cells to reflect skull presence and health. When the user wishes to adjust the number of available chess pieces, they double-click the numerical counter next to each piece icon and type a new value, or use the small up and down arrows to increment or decrement the count. The grid and counters always remain visible, so the user can experiment freely without losing sight of their puzzle layout.

## Puzzle Solving Flow
Once the board layout and piece counts are set, the user clicks the Solve button. The editor starts the beam search algorithm in a background thread so the interface does not freeze. While the search runs, a small progress label reads “Solving…” and a Stop button appears, allowing the user to cancel the search at any time. If the user clicks Stop, the algorithm halts and the label reverts to the default message. When the solver finds a valid sequence of piece placements that eliminates all skulls, the Pygame window remains in view but a separate Tkinter Solution Window pops up on top. This window shows each placement step in text form, for example, “Place Queen at D5 to remove two skulls.” The main editor does not accept new inputs while the solution window is displayed, signaling that the solving phase is complete.

## Solution Window and Returning to the Editor
In the Solution Window, the user can scroll through the list of moves to review the solver’s decisions and then click a Close button at the bottom. Closing the solution window immediately returns focus to the main Pygame editor, where the user can clear the board, adjust piece counts or skull placements, and run another solve. The grid remains in its last edited state, so users can iterate quickly on puzzle designs based on the reported solution.

## Settings and Configuration Management
ChessBomb Editor does not feature an in-app settings panel. Instead, core parameters such as beam width, maximum search depth, and color themes are defined in a small configuration file or at the top of the Python script. Advanced users who wish to customize these values must edit the configuration variables before launching the application. Any changes to the configuration take effect the next time the user restarts the editor. User preferences like window size or last opened board are not stored persistently.

## Error States and Alternate Paths
If the user enters an invalid piece count, such as a negative number or non-numeric input, the editor clamps the value to zero and displays a brief warning message field above the counters. Attempting to place more pieces than allowed or exceeding grid bounds simply has no effect, and the cursor changes to a “not allowed” icon. During solving, if the maximum depth is reached or no solution exists, the background thread terminates and the progress label switches to “No solution found.” The Stop button disappears and the user can tweak the board or piece counts and retry. Any unexpected errors in the solver or GUI trigger a popup dialog showing the error details and instructions to restart the application.

## Conclusion and Overall App Journey
From launch through puzzle creation and solution review, ChessBomb Editor guides the user in a single cohesive window supported by a simple popup for results. A new user quickly learns to place skulls, adjust piece counts, and run the solver without navigating through complex menus. The application maintains responsiveness by running heavy computations in the background and clearly signals each phase of the workflow. When the user closes the solution window, they return to the editor with their puzzle intact and can immediately iterate, refining layouts or changing parameters until they achieve the desired challenge or solution sequence.
